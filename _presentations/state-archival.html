State Archival

Most of the state is dead weight. Move it out of the database, keep the state root identical, and let the trie resurrect it on demand.

go-ethereum #33906 NO HARD FORK Guillaume Ballet
Terminal Ledger
part 1 · the problem

The database gets slower as it gets fuller

  • Every block re-hashes each dirty path to the root and persists the nodes it touched
  • Those writes land scattered across a keyspace that is mostly cold
  • LSM compaction and page copy-on-write then rewrite far more bytes than the block changed
  • So per-block cost tracks total state size, not the size of the change

Scale, early 2026: ~360M accounts, ~1.5B storage slots (figures from EIP-8188's rationale).

part 1 · the observation

But almost nothing moves

The other 97% is paying rent in the hot path and never showing up for work. Measurement ongoing — treat the exact figure as provisional.

01 · Problem
part 2 · precedent

History expiry already made this move

  • 400+ GB of headers, bodies and receipts that no block needs to validate the tip
  • Clients stopped serving anything older than a year over p2p, and pruned it locally
  • The data did not die — it moved out of band: flat era files, torrents, indexers
  • Consensus never noticed. Disk requirements dropped anyway
  • If a significant portion of the state is "cold", the same method can be applied.

EIP-4444 is still formally Stagnant. Clients pruned history anyway, behind flags. Remember that when we get to the roadmap.

02 · Precedent
part 3 · the method

Expire internal nodes, keep the leaves

  • Walk the trie and pick subtrees at height 3 — height counted from the leaves, so leaves are 0
  • Append their leaf records to one flat file: <datadir>/geth/nodearchive
  • Delete every node of that subtree from the DB, leave a stub holding offset + size
  • Keep the subtree root hash, so the state root does not change
  • Need it again? Load the records back into memory — reading never hashes, only writing does
03 · Method

What the swap looks like

03 · Method

The replacement is 17 bytes

type expiredNode struct {
    offset          uint64 // where the leaves live
    size            uint64 // how many bytes to read
    cachedHash      hashNode // subtree root: consensus unchanged
    archiveResolver archive.ResolverFn
}

In db: 1 marker byte + 8 offset + 8 size. A whole subtree collapses to that.

03 · Method
read path vs write path

Reads don't hash — writes do

  • Read: load the records at (offset, size) into memory, return the leaf you asked for — zero hashes
  • Write: the new value invalidates the hashes above it, so that path is rebuilt and re-persisted
  • Untouched siblings never come back as nodes — they become new expiredNodes, offset and size rewritten

A write costs one path, not one subtree, and nothing already in the archive is invalidated. Re-hashing cost is what grows with subtree height — that's the real reason height 3 is the sweet spot.

03 · Method
why it wins

A flat file beats a database

CHEAPER

  • One seek at a known offset — no index descent, no page cache miss
  • Fewer live nodes → smaller working set, less compaction

PRICIER

  • Writes must rebuild before they can mutate
  • Extra hashing on the commit path
  • …both dwarfed by the I/O they replace

The trie stops paying for generality it never uses on cold data.

03 · Method
part 4.1 · what this unlocks

Delete the file and you have state expiry

What you give up is the ability to answer for that subtree — so something has to hand the leaves back, exactly like history: a peer, a proof, or a third party. This is the design space the PR opens, not what it implements today.

04 · What to build
part 4.2 · what this unlocks

EIP-8188: put the write age in the state

// one new field, on every account and every slot
- account    = RLP([nonce, balance, storageRoot, codeHash])
+ account    = RLP([nonce, balance, storageRoot, codeHash, last_written_block])

- slot_value = RLP(value)
+ slot_value = RLP([value, last_written_block])

Old entries stay readable: a 4-element account decodes as 0, and a bare slot bytestring (0x80+) is told apart from the new list (0xc0+) by its RLP prefix. Hard fork, but no tree transition.

04 · What to build
part 4.2 · how it works

Written, never read

  • A write stamps block_number on the entry; writing twice in one block is idempotent
  • Storage writes cascade to the account — its storageRoot changed anyway
  • Reads never stamp: otherwise SLOAD becomes a write and STATICCALL stops being static (EIP-214)
  • Reverts restore it like balance or nonce
  • Cost: 5 bytes per account, 6 per slot — ~10.8 GB worst case, and only for state written post-fork

Then archival stops guessing which subtrees are cold: every client reads the same consensus-verified write age and picks the same set.

05 · Numbers
part 5 · why they disagree

Treeception: our tree lives in its tree

  • The database keeps our trie inside its own tree — pages, levels, indexes. Cost per access tracks that depth, so it is logarithmic in DB size
  • Hoodi is small enough to sit on the steep part: delete data and a whole level disappears
  • Mainnet's hot set alone is bigger than all of hoodi. It is already on the flat part, so −27% of the bytes removes no level — and the little it gains is eaten by resurrections
  • That flips when mainnet crosses ≈5 TB and the next level lands: same archival, real speedup
05 · Numbers
part 6 · the actual point

Out of protocol beats in protocol

  • ACD tries to estimate the impact of a change before implementing it - this is a long and error-prone process
  • Out-of-protocol: no fork window, no cross-client rollout
  • The measurement comes first, and the EIP comes later with data already attached
  • Consensus is the tool of last resort — for what genuinely needs it, like 8188's metadata
