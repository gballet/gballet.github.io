State Archival

Most of the state is dead weight. Move it out of the database, keep the state root identical, and let the trie resurrect it on demand.

$ du -sh chaindata 02 / 17
the problem

The database gets slower as it gets fuller

  • Every block re-hashes each dirty path to the root and persists the nodes it touched
  • Those writes land scattered across a keyspace that is mostly cold
  • LSM compaction and page copy-on-write then rewrite far more bytes than the block changed
  • So per-block cost tracks total state size, not the size of the change

Scale, early 2026: ~360M accounts, ~1.5B storage slots (figures from EIP-8188's rationale).

precedent

We already solved this shape of problem

THEN · history

  • Block count and size outgrew the database
  • Old blocks were moved to an archive outside the DB
  • Rarely read, so the trade was obvious

NOW · state

  • Same growth curve, same DB pressure
  • Cold state moves to an archive file, hot state stays
  • Bonus: an unused subtree can be dropped entirely and rebuilt from its leaves
02 · Idea
$ cat trie/archiver.go 05 / 17
the idea

Expire the subtree, keep the leaves

  • Walk the trie and pick subtrees at height 3 — height counted from the leaves, so leaves are 0
  • Append their leaf records to one flat file: <datadir>/geth/nodearchive
  • Delete every node of that subtree from the DB, leave a stub holding offset + size
  • Keep the subtree root hash, so the state root does not change
  • Need it again? Read the leaves back and re-hash 3 levels on the fly

On disk: 1 marker byte + 8 offset + 8 size. A whole subtree collapses to that.

03 · Mechanism
$ archive verify --hoodi 08 / 17
resurrection

Reading a cold node is just hashing

  • Resolver reads the records at (offset, size) — one seek into a flat file
  • Leaves are re-inserted, the subtree is rebuilt, hashes recomputed bottom-up
  • The result is checked against the stored subtree root: no trust required
  • geth archive verify does this for every archived node, accounts and storage

Hashing work grows exponentially with subtree height. Height 3 rebuilds in negligible time; go deeper and the resurrection cost is what bites you. That's the whole reason the knob exists.

03 · Mechanism
$ perf stat -- geth import 09 / 17
the counterintuitive part

A flat file beats a database

CHEAPER

  • One seek at a known offset — no index descent, no page cache miss
  • Fewer live nodes → smaller working set, less compaction

PRICIER

  • Writes must rebuild before they can mutate
  • Extra hashing on the commit path
  • …both dwarfed by the I/O they replace

The trie stops paying for generality it never uses on cold data.

03 · Mechanism
$ geth archive --help 10 / 17

One command, four subcommands

$ geth archive generate --hoodi        # walk trie, archive height-3 subtrees
$ geth archive verify --hoodi          # resurrect everything, compare hashes
$ geth archive check-node --owner H --path N
$ geth archive delete-journal --hoodi  # drop pathdb journal after generate

# knobs: --output, --compaction-interval 1000, --dry-run

Reads nodes straight from the persistent disk layer, bypassing in-memory diff layers, so what it archives is what is actually on disk.

What it costs

  • +2 GB chaindata in the benchmark — the archive itself is 2.1 MB, the rest is layout churn
  • A 53-minute offline pass before the win starts
  • The pathdb journal must be dropped afterwards, or in-memory layers disagree with disk
  • Height is a real trade: deeper subtrees archive more, resurrect slower
  • Naming is already contested — review suggests geth trie compress, since this is offline compression, not "archive mode"

$ whoami --no-fork-required 15 / 17
the actual point

This lives outside the protocol

Same state root. Same blocks. Same consensus. Nothing to negotiate.
  • No EIP, no fork window, no cross-client coordination
  • Opt-in per node, and reversible: verify, then walk it back if you don't like it
  • Iterate at client speed instead of fork cadence
  • Measure on a real chain first; only ask for protocol changes you have data for
05 · Argument
$ open eips.ethereum.org/EIPS/eip-8188 16 / 17
better together

Where the protocol does help

  • EIP-8188 records last_written_block on every account and slot
  • A consensus-verified write age: every client picks the same cold set, instead of guessing from local caches
  • Reads never bump it — otherwise a read becomes a write and STATICCALL breaks
  • Cost: 5 bytes per account, 6 per slot — ~10.8 GB worst case, and that buys targeted archival

Client-side archival works today on heuristics; write-age metadata turns it from a guess into a decision.
